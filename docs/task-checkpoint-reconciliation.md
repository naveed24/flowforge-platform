# Manual task checkpoint reconciliation

This is an **internal service**, not a public HTTP endpoint or automatic remote-result verifier. A worker crash can leave an `IN_PROGRESS` checkpoint even when the remote operation completed. Operators must independently inspect the remote system using its stable idempotency key and record a durable evidence reference before invoking `TaskCheckpointReconciliationService.reconcile`.

- `REMOTE_SUCCEEDED`: remote operation is independently confirmed; checkpoint becomes `SUCCEEDED` and cannot be replayed.
- `REMOTE_DID_NOT_EXECUTE`: remote operation is conclusively known not to have occurred; checkpoint becomes `RETRYABLE`. Only a **later RUNNING execution attempt** can claim it again.
- Unknown, timeout, partial, or contradictory evidence: **do not reconcile**. Leave the checkpoint `IN_PROGRESS`.

Evidence references are trimmed and must contain 1–512 visible characters. Control characters, line breaks, and invisible Unicode formatting characters are rejected to prevent multiline or visually misleading audit entries. Use an independently verifiable provider receipt, immutable incident ticket, or similar durable identifier; never put secrets or raw credentials in evidence references. Invalid evidence is rejected before any checkpoint transition or audit write.

The service requires the checkpoint's exact attempt and UUID claim token. It locks the parent execution row, compares current checkpoint state and ownership, and writes an audit row in the same database transaction as the transition. Repeated/stale reconciliation fails without a new audit row. Evidence is a reference to independent proof, not proof by itself. The audit is retained independently of checkpoint cleanup: PostgreSQL rejects deletion of a checkpoint with reconciliation audit history (including deletion through a parent execution cascade). Operators must use an explicit, reviewed retention process rather than accidentally erasing evidence during cleanup. V16 rejects UPDATE and DELETE on audit rows through a database trigger; V17 also rejects TRUNCATE (which does not fire row-level DELETE triggers), including when the table is empty. These safeguards protect against ordinary application or operator SQL, not privileged schema changes by database owners or superusers. A future legally approved retention process must explicitly design and review its handling of this append-only guard; do not disable the trigger as routine cleanup. Protect backups and access accordingly.

Reconciliation does not change execution status, automatically restart a failed/cancelled workflow, authorize remote calls, or provide exactly-once semantics. **Do not expose this internal service to users without authentication, authorization, approval controls, and audit retention policy.**
